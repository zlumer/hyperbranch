# Task run full cycle

The vision is as follows:
1. User can launch a web interface and see the list of current tasks in the kanban.
2. User can press a button in the web ui to create a new task (with a title input and text input).
3. The task is created similar to the `hb create` command.
4. User can press a button in the web ui to launch this task into a run (similar to `hb run`).
5. Logically, user can also see the list of current runs for the task and their statuses.
6. User can press a button in the web ui next to run info and "jump into the run".
7. "Jumping into the run" opens Opencode web UI in the iframe (almost fullscreen with just a "back" button).
8. Pressing the back button returns to the main UI.
9. User can delete a run with the "remove" button.
10. When the run is started, the prompt is sent to opencode to plan the task thoroughly.
11. User should be able to customise the run prompt and agent mode: Plan or Build when they create a run.
12. User should be able to accept the run: merge the branch and delete it.

This is the MVP of working with tasks, when we have that scenario working we can actually test the workflow without the CLI workarounds and manual git commits/merges.

### Implementation Plan

**1. Frontend: Task Creation & Board Updates**
* **Modal Task Creation**:
  * Add a "+ Create Task" button at the bottom of each column in the Kanban board (`Board.tsx` / `TaskCard.tsx`).
  * Clicking it opens a Modal Dialog with inputs for **Title** (required) and **Description** (textarea).
  * The new task's default status will be determined by the **contextual column** the button was clicked in.
  * Submits a `POST /tasks` request.
* **Live Status Updates via WebSockets**:
  * The `TaskDetailsPage` will connect to a new dedicated WebSocket endpoint (`/tasks/:taskId/runs/status` or similar) to listen for run status changes in real-time.

**2. Frontend: Run Configuration & Launching**
* **Inline Run Configuration**:
  * On the `TaskDetailsPage`, the "Launch Run" button will expand an inline configuration section.
  * **Run Prompt (Textarea)**: Defaults to `@.hyperbranch/tasks/task-<taskId>.md Please plan and execute this task.` (using the `@` file tagging).
  * **Agent Mode (Dropdown)**: Default dynamically depends on task status: `plan` or `todo` -> Plan mode. `build` -> Build mode.
  * Clicking "Confirm Launch" sends the configured `{ prompt, agentMode }` payload to `POST /tasks/:id/run`.

**3. Frontend: Iframe Workspace & Actions**
* **The Fullscreen Iframe**:
  * The `RunWorkspacePage` (`/tasks/:taskId/runs/:runId/workspace`) will replace the current split-pane with an almost-fullscreen `<iframe />`.
  * The frontend will fetch the mapped port for the run from the backend and set the iframe source to `http://localhost:<mapped-port>`.
* **Top Navigation Bar**:
  * A slim navigation bar above the iframe containing a **Back** button and an **Accept Run** button.
* **Deleting a Run**:
  * Located on the `TaskDetailsPage` next to each run in the list.
  * Clicking "Delete" opens a **Confirmation Dialog**. Calls `DELETE /tasks/:id/runs/:runId`.
* **Accepting a Run**:
  * Located in both the `TaskDetailsPage` and the **Iframe Header**.
  * Clicking it presents a dropdown for **Merge Strategy** (`merge`, `squash`, `rebase`).
  * Executes the merge by calling `POST /tasks/:id/runs/:runId/merge`.

**4. Backend: API Endpoints**
* **Port Mapping Endpoint**:
  * Implement `GET /tasks/:id/runs/:runId/port` which utilizes `Runs.getHostPort(runId, 4096)`.
* **Run Deletion Endpoint**:
  * Implement `DELETE /tasks/:id/runs/:runId` mapping to `Runs.removeRun(taskId, runIndex, force)`.
* **Dedicated Status WebSocket**:
  * Create a WebSocket endpoint (e.g., `GET /tasks/:id/runs/status`) that streams real-time status updates down to the client.

**5. Backend: Opencode SDK Integration (Post-start Request)**
* **Asynchronous Initialization**:
  * `POST /tasks/:id/run` starts the Docker container and immediately returns `runId` and `port`.
  * A background async routine will inject the prompt.
* **Health Polling**:
  * The background routine polls `http://localhost:<mapped-port>/global/health` using `fetch` until it receives `{ healthy: true }`.
* **SDK Prompt Injection**:
  * Add `@opencode-ai/sdk` to the CLI's dependencies (`npm:@opencode-ai/sdk`).
  * Instantiate the SDK client pointing to the mapped port.
  * Create a new session specifically for this run.
  * Use the Session endpoint to inject the user's configured prompt and agent mode: `client.session.prompt({ ... })`.
* **Error Handling**:
  * If polling times out or SDK request fails, mark the run as failed.
